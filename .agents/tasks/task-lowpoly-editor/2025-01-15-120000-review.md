# Browser-based low-poly 3D model editor

A greenfield Vite + TypeScript + Three.js application implementing a low-poly 3D editor with primitive creation, four edit modes (Object, Vertex, Edge, Face), face extrusion, per-face painting, flat/smooth shading toggle, undo/redo, and export to glTF/OBJ. The architecture is a central `Editor` class that owns a viewport, selection manager, mode state machine, and a command-pattern history stack. UI classes bind DOM elements to editor methods. The entire interface is in Russian.

**Watch for:** History bypasses that break undo consistency (confirmed), grid snapping declared but never wired into actual vertex/object manipulation (confirmed), memory leaks from highlight meshes created on every mousemove in face mode (confirmed), and extrusion destroying vertex colors (confirmed).

## High-level view

The editor is a single-scene application where `Viewport` owns the Three.js renderer and `Editor` composes all subsystems as the facade that UI calls into. The history system uses a classic command pattern with `execute`/`undo` pairs, but five subsystems bypass the public `push()` method and reach directly into private stacks — breaking max-size enforcement and any future middleware.

Vertex mode creates per-vertex marker meshes and implements drag-to-move via raycasting against a camera-facing plane. Undo actions identify vertices by floating-point position matching, which becomes unreliable after compound edits. Edge mode is selection-only with no manipulation capability. Face mode supports both selection highlighting and per-face color painting through vertex colors, but the highlight mesh is recreated on every mousemove event.

Grid snapping exists as a standalone utility class but is never called by any manipulation code. The `TransformTool` and `FacePainter` classes are dead code — their functionality either lives elsewhere or was never connected.

1. **History stack bypass** — `ObjectMode`, `VertexMode`, `FaceMode.paintFace`, `ExtrudeTool`, and `DeleteTool.deleteFace` all push directly to `this.history['undoStack']` instead of calling `history.push()`. 2. **Grid snap is dead code** — `GridSnap.snapToGrid()` and `TransformTool.snapValue()` are never called during vertex dragging or TransformControls manipulation. The UI toggle has no effect on actual movement. (confirmed)
3. **Highlight mesh leak on rapid mousemove** — `FaceMode.onMouseMove` allocates a new `BufferGeometry` and `MeshBasicMaterial` on every event (~60/sec while hovering). Use a persistent highlight mesh with in-place geometry updates instead. (confirmed)
4. **Vertex match-by-position fragility** — Undo in `VertexMode` locates vertices by comparing positions with 0.0001 tolerance. After extrusion or multiple edits, unrelated vertices may match or the target may drift beyond tolerance. Store vertex indices instead. (likely)

6. **SelectionManager dispose is broken** — `dispose()` passes a new `.bind(this)` reference to `removeEventListener`, which never matches the one registered in the constructor. The click listener is never removed. (confirmed)
7. **Properties panel has no live update** — Transform values update only on selection change, not during TransformControls dragging. Numeric inputs become stale until reselection. (confirmed)

## History command bypass pattern

The `History` class exposes a clean `push(action)` method that executes the action immediately, clears the redo stack, and enforces max size. Five call sites bypass this:

```typescript
// ObjectMode, VertexMode, FaceMode.paintFace, ExtrudeTool, DeleteTool.deleteFace
this.history['undoStack'].push(action);
this.history['redoStack'] = [];
```

The intent is to record an already-completed action without re-executing it. But this bypasses max-size enforcement — directly-pushed actions accumulate unbounded beyond the 50-item cap. A `record(action)` method that stores without executing would unify these call sites.

## Grid snap is declared but disconnected

`GridSnap` and `TransformTool` both implement snap-to-grid math, but neither is wired into anything that moves geometry. In Object mode, `TransformControls` has a `translationSnap` property that is never set. In Vertex mode, `onMouseMove` updates vertex positions from the raycasted intersection point with no snapping applied. The grid-snap button toggles an internal boolean that nothing reads during manipulation.

## Face highlight allocation pressure

`FaceMode.onMouseMove` creates a new `BufferGeometry` and `MeshBasicMaterial` on every mouse event, disposes the previous one, and adds/removes from the scene. At ~60 events/second while hovering over a mesh, this is a high-frequency allocation pattern. Three.js disposal flags GPU resources for deletion but doesn't guarantee immediate reclamation. A persistent highlight mesh whose geometry buffer is updated in place would eliminate this churn.

## Vertex identification by position breaks after compound edits

Both the real-time drag and the undo action in `VertexMode` find all vertices matching a position within `0.0001` tolerance. This becomes unreliable when:

- Two originally distinct vertices are moved to the same location (subsequent undo moves both)
- Floating-point drift from multiple moves accumulates beyond the tolerance (undo misses the target)
- Extrusion creates new vertices at the same position as old ones

Storing vertex indices rather than positions would be more robust.

## Extrusion drops non-position attributes

`ExtrudeTool.extrude` builds new geometry by copying raw position floats into a new array and appending side-face vertices. It never copies `color`, `uv`, or `normal` attributes from the source geometry. The paint → extrude workflow destroys all prior face colors with no warning to the user.

## SelectionManager event listener leak

```typescript
// In constructor:
container.addEventListener('click', this.onMouseClick.bind(this));

// In dispose:
this.container.removeEventListener('click', this.onMouseClick.bind(this));
```

Each `.bind(this)` creates a new function reference. The `removeEventListener` call never matches the registered listener. The fix is to store the bound reference (as the mode classes correctly do with their `*Bound` properties).

## Dead code: FacePainter and TransformTool

`src/editor/painting/FacePainter.ts` and `src/editor/tools/TransformTool.ts` are never instantiated or referenced anywhere. Their functionality either lives directly in `FaceMode` (painting) or in Three.js `TransformControls` via `ObjectMode` (transforms). These should be removed or integrated.
